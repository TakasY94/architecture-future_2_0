# Описание ключевых агрегатов

## Введение

Агрегаты представляют собой кластеры связанных объектов, которые рассматриваются как единое целое для целей изменения данных. Каждый агрегат имеет корень (Aggregate Root), который является единственной точкой входа для операций с агрегатом.

## Медицинский домен

### 1. Агрегат: Пациент (Patient)
**Корень агрегата**: `Patient`
**Границы агрегата**: Включает основную информацию о пациенте, контактные данные, историю регистраций и ссылки на медицинские карты.

**Сущности внутри агрегата**:
- `Patient` (корень) - основная информация о пациенте
- `ContactInfo` - контактная информация
- `RegistrationHistory` - история регистраций в клиниках
- `InsuranceInfo` - страховые данные

**Инварианты**:
- У пациента должен быть уникальный идентификатор (PatientID)
- Email и телефон должны быть валидными (если указаны)
- Дата рождения не может быть в будущем
- Пациент не может быть удален, только деактивирован (soft delete)

**Ключевые операции**:
- `registerPatient()` - регистрация нового пациента
- `updateContactInfo()` - обновление контактных данных
- `deactivatePatient()` - деактивация пациента
- `addInsurance()` - добавление страховой информации

**Публикуемые события**:
- `PatientRegistered`
- `PatientContactInfoUpdated`
- `PatientDeactivated`

### 2. Агрегат: Медицинская карта (MedicalRecord)
**Корень агрегата**: `MedicalRecord`
**Границы агрегата**: Включает историю болезней, диагнозы, назначения, результаты исследований и лечения.

**Сущности внутри агрегата**:
- `MedicalRecord` (корень) - основная медицинская карта
- `Diagnosis` - поставленные диагнозы
- `Appointment` - записи на приемы
- `TreatmentPlan` - планы лечения
- `TestResult` - результаты анализов и исследований

**Инварианты**:
- Медицинская карта должна быть привязана к пациенту
- Каждый диагноз должен иметь дату постановки и врача
- Назначения не могут пересекаться по времени для одного врача
- Результаты исследований должны иметь ссылку на тип исследования

**Ключевые операции**:
- `addDiagnosis()` - добавление диагноза
- `scheduleAppointment()` - создание назначения
- `recordTestResult()` - запись результатов исследования
- `updateTreatmentPlan()` - обновление плана лечения

**Публикуемые события**:
- `MedicalRecordCreated`
- `DiagnosisAdded`
- `AppointmentScheduled`
- `TestResultRecorded`

### 3. Агрегат: Назначение (Appointment)
**Корень агрегата**: `Appointment`
**Границы агрегата**: Включает информацию о записи на прием, статусе, времени и участниках.

**Сущности внутри агрегата**:
- `Appointment` (корень) - основная информация о назначении
- `TimeSlot` - временной слот
- `Participant` - участники (пациент, врач, медсестра)
- `Reminder` - напоминания о назначении

**Инварианты**:
- Назначение должно иметь хотя бы одного врача и пациента
- Время назначения не может быть в прошлом при создании
- Назначение не может быть создано для неактивного пациента
- Врач не может иметь пересекающихся назначений

**Ключевые операции**:
- `createAppointment()` - создание назначения
- `cancelAppointment()` - отмена назначения
- `rescheduleAppointment()` - перенос назначения
- `markAsCompleted()` - отметка о выполнении

**Публикуемые события**:
- `AppointmentCreated`
- `AppointmentCancelled`
- `AppointmentRescheduled`
- `AppointmentCompleted`

## Финансовый домен

### 4. Агрегат: Счет (Account)
**Корень агрегата**: `Account`
**Границы агрегата**: Включает информацию о счете, балансе, владельце и истории транзакций.

**Сущности внутри агрегата**:
- `Account` (корень) - основная информация о счете
- `Balance` - текущий баланс и лимиты
- `AccountHolder` - владелец счета
- `Transaction` - транзакции по счету

**Инварианты**:
- Баланс не может быть отрицательным без овердрафта
- Каждая транзакция должна иметь уникальный идентификатор
- Сумма транзакции должна быть положительной
- Счет должен быть привязан к клиенту

**Ключевые операции**:
- `openAccount()` - открытие счета
- `deposit()` - пополнение счета
- `withdraw()` - снятие средств
- `transfer()` - перевод между счетами
- `closeAccount()` - закрытие счета

**Публикуемые события**:
- `AccountOpened`
- `DepositMade`
- `WithdrawalMade`
- `TransferCompleted`
- `AccountClosed`

### 5. Агрегат: Кредитный договор (LoanContract)
**Корень агрегата**: `LoanContract`
**Границы агрегата**: Включает условия кредита, график платежей, историю выплат и статус.

**Сущности внутри агрегата**:
- `LoanContract` (корень) - основной договор
- `LoanTerms` - условия кредита (сумма, процент, срок)
- `PaymentSchedule` - график платежей
- `PaymentHistory` - история выплат
- `Collateral` - обеспечение по кредиту

**Инварианты**:
- Сумма кредита должна быть положительной
- Процентная ставка должна быть в допустимых пределах
- Дата выдачи не может быть позже первой даты платежа
- Клиент должен пройти кредитную проверку

**Ключевые операции**:
- `createLoanContract()` - создание кредитного договора
- `approveLoan()` - одобрение кредита
- `recordPayment()` - запись платежа
- `restructureLoan()` - реструктуризация кредита
- `writeOffLoan()` - списание кредита

**Публикуемые события**:
- `LoanContractCreated`
- `LoanApproved`
- `PaymentReceived`
- `LoanRestructured`
- `LoanWrittenOff`

## ИИ-сервисы домен

### 6. Агрегат: Модель ИИ (AIModel)
**Корень агрегата**: `AIModel`
**Границы агрегата**: Включает метаданные модели, версии, метрики качества и историю обучения.

**Сущности внутри агрегата**:
- `AIModel` (корень) - основная информация о модели
- `ModelVersion` - версии модели
- `TrainingMetrics` - метрики обучения
- `PerformanceStats` - статистика производительности
- `DatasetReference` - ссылки на обучающие данные

**Инварианты**:
- Модель должна иметь уникальный идентификатор
- Каждая версия должна иметь тег версии
- Метрики качества должны быть в допустимых пределах
- Модель должна быть проверена перед использованием в production

**Ключевые операции**:
- `registerModel()` - регистрация новой модели
- `trainModel()` - обучение модели
- `validateModel()` - валидация модели
- `deployModel()` - деплой модели
- `retireModel()` - вывод модели из эксплуатации

**Публикуемые события**:
- `AIModelRegistered`
- `ModelTrained`
- `ModelValidated`
- `ModelDeployed`
- `ModelRetired`

### 7. Агрегат: Анализ исследования (ResearchAnalysis)
**Корень агрегата**: `ResearchAnalysis`
**Границы агрегата**: Включает исходные данные исследования, результаты анализа ИИ, уверенность модели и рекомендации.

**Сущности внутри агрегата**:
- `ResearchAnalysis` (корень) - основной анализ
- `ResearchData` - исходные данные исследования
- `AIResult` - результаты анализа ИИ
- `ConfidenceScore` - оценка уверенности
- `Recommendation` - рекомендации по результатам

**Инварианты**:
- Анализ должен быть привязан к конкретному исследованию
- Результаты должны иметь временную метку
- Уверенность модели должна быть в диапазоне 0-100%
- Рекомендации должны соответствовать результатам анализа

**Ключевые операции**:
- `initiateAnalysis()` - инициирование анализа
- `processWithAI()` - обработка данных ИИ
- `generateReport()` - генерация отчета
- `flagAnomaly()` - пометка аномалии

**Публикуемые события**:
- `AnalysisInitiated`
- `AIProcessingCompleted`
- `ReportGenerated`
- `AnomalyDetected`

## Аналитический домен

### 8. Агрегат: Отчет (Report)
**Корень агрегата**: `Report`
**Границы агрегата**: Включает метаданные отчета, параметры, сгенерированные данные и историю доступа.

**Сущности внутри агрегата**:
- `Report` (корень) - основной отчет
- `ReportParameters` - параметры отчета
- `GeneratedData` - сгенерированные данные
- `AccessLog` - история доступа к отчету
- `VisualizationConfig` - конфигурация визуализации

**Инварианты**:
- Отчет должен иметь уникальный идентификатор
- Параметры должны быть валидными для типа отчета
- Данные должны соответствовать схеме отчета
- Доступ должен контролироваться правами пользователя

**Ключевые операции**:
- `createReport()` - создание отчета
- `generateData()` - генерация данных
- `scheduleReport()` - планирование отчета
- `shareReport()` - предоставление доступа к отчету
- `archiveReport()` - архивирование отчета

**Публикуемые события**:
- `ReportCreated`
- `DataGenerated`
- `ReportScheduled`
- `ReportShared`
- `ReportArchived`

### 9. Агрегат: Дашборд (Dashboard)
**Корень агрегата**: `Dashboard`
**Границы агрегата**: Включает виджеты, компоновку, данные в реальном времени и настройки пользователя.

**Сущности внутри агрегата**:
- `Dashboard` (корень) - основной дашборд
- `Widget` - виджеты на дашборде
- `Layout` - компоновка виджетов
- `RealTimeData` - данные в реальном времени
- `UserPreferences` - настройки пользователя

**Инварианты**:
- Дашборд должен иметь владельца
- Виджеты должны быть совместимы с типами данных
- Компоновка должна быть валидной
- Данные должны обновляться в соответствии с настройками

**Ключевые операции**:
- `createDashboard()` - создание дашборда
- `addWidget()` - добавление виджета
- `updateLayout()` - обновление компоновки
- `refreshData()` - обновление данных
- `cloneDashboard()` - клонирование дашборда

**Публикуемые события**:
- `DashboardCreated`
- `WidgetAdded`
- `LayoutUpdated`
- `DataRefreshed`
- `DashboardCloned`

## Управление персоналом домен

### 10. Агрегат: Сотрудник (Employee)
**Корень агрегата**: `Employee`
**Границы агрегата**: Включает личную информацию, должность, отдел, компетенции и историю работы.

**Сущности внутри агрегата**:
- `Employee` (корень) - основная информация о сотруднике
- `Position` - должность и роль
- `Department` - отдел
- `Competency` - компетенции и навыки
- `WorkHistory` - история работы в компании

**Инварианты**:
- Сотрудник должен иметь уникальный идентификатор
- Должность должна быть валидной для отдела
- Компетенции должны соответствовать должности
- Дата приема не может быть в будущем

**Ключевые операции**:
- `hireEmployee()` - прием на работу
- `updatePosition()` - изменение должности
- `addCompetency()` - добавление компетенции
- `transferDepartment()` - перевод в другой отдел
- `terminateEmployment()` - увольнение

**Публикуемые события**:
- `EmployeeHired`
- `PositionUpdated`
- `CompetencyAdded`
- `DepartmentTransferred`
- `EmploymentTerminated`

## Принципы проектирования агрегатов

1. **Инкапсуляция бизнес-правил**: Все инварианты защищены внутри агрегата
2. **Согласованность в границах транзакций**: Изменения внутри агрегата атомарны
3. **Минимизация размера**: Агрегаты должны быть как можно меньше, но не меньше
4. **Ссылки по идентификаторам**: Внешние ссылки используют ID, а не объекты
5. **Event Sourcing готовность**: Агрегаты спроектированы для публикации событий
6. **Идемпотентность операций**: Повторное выполнение операций дает тот же результат
